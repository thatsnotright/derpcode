# Review notes: event-bus

## Planted issues

1. **`bus.go: Publish` does a blocking send (`ch <- ev`) while holding `RLock`.** One subscriber that stops reading and has a full buffer parks the publisher forever; it still holds the read lock, so every later `Subscribe`/`Close` (which need the write lock) blocks too, and `RWMutex` then blocks new readers behind the waiting writer: the whole bus freezes. This is the "audit component hangs in staging" symptom. Fix: non-blocking send (`select { case ch <- ev: default: }`) and document the drop policy (or a per-subscriber goroutine/queue if loss is not acceptable). Caught by: `TestSlowSubscriberDoesNotBlockOthers` (and as a hang in the stress test).
2. **`bus.go: Subscribe`'s unsubscribe function mutates the map and closes the channel under `RLock`.** Read locks do not exclude each other, so `delete` races with `Publish` ranging over the same map (data race / `fatal error: concurrent map iteration and map write`), and `close(ch)` can run while a `Publish` is sending on it (`panic: send on closed channel`: the staging panic). Fix: take the write lock for anything that mutates state, and keep sends under the read lock non-blocking so a close can never overlap a send. Caught by: `-race` in `TestConcurrentPublishSubscribeUnsubscribe`, `TestUnsubscribeClosesChannelAndStopsDelivery`.
3. **`bus.go: Subscribe`'s unsubscribe is not idempotent.** The second call closes an already closed channel (`panic: close of closed channel`), and after `Bus.Close` any later unsubscribe does the same. Callers legitimately `defer unsub()` and also unsubscribe on error paths. Fix: check that the subscription is still registered (under the write lock) before deleting and closing, or use a `sync.Once` per subscription. Caught by: `TestUnsubscribeTwiceIsSafe`, `TestUnsubscribeAfterCloseIsSafe`.
4. **`bus.go: Close` is not idempotent and leaves the bus usable.** A second `Close` double-closes every channel and panics; `Publish` after `Close` sends on closed channels (panic); `Subscribe` after `Close` registers a channel nobody will ever close. Fix: a `closed` flag checked in `Close`/`Subscribe`/`Publish`, reset `subs`, and return an already closed channel from `Subscribe` on a closed bus. Caught by: `TestCloseClosesSubscribersAndIsIdempotent`, `TestUseAfterClose`.
5. **`bus.go: Once` ignores `ctx` and the "closed" signal of the subscription channel.** The goroutine blocks on `<-ch` forever when no event arrives, so every cancelled `Once` leaks a goroutine, a subscription and a channel (an easy leak under request-scoped use). When the bus closes, `<-ch` returns the zero `Event` and `Once` delivers a bogus empty event. Fix: `select` on `ch` and `ctx.Done()`, use the `ok` from the receive, `defer close(out)`. Caught by: `TestOnceStopsWhenContextIsCancelled`, `TestOnceOnClosedBusDeliversNothing`.
6. **Review only: API and robustness.** `Subscribe` with a negative buffer panics in `make`; a dropped event is invisible (no counter, log or doc), so the next engineer cannot tell lossy from reliable; empty topics are never removed from `subs` (slow leak with per-request topics: the reference deletes them); `Event.Data` is a `string`, so structured payloads need a marshal/unmarshal convention (generics `Bus[T]`, or `any` with typed helpers); delivery order across subscribers is map-random (fine, but say so); `Once` has no way to be unsubscribed other than ctx; a `Subscribe(ctx, ...)` variant that unsubscribes on cancel would remove most caller-side cleanup.

## Coaching / best-practice talking points

- Channels: only the *sender side* closes, and only when it knows nobody will send again. Here the bus owns both, so closing must be serialised with sending by the same lock.
- A lock is not a license to block: never perform an operation that can block indefinitely (channel send, network call, callback) while holding a mutex. Either make it non-blocking, or copy what you need under the lock and do the slow part outside, accepting the consequences for closing.
- `RLock` means "I only read". Any `delete`, `close`, assignment or counter increment needs `Lock`. `RWMutex` also has writer-preference: one blocked writer stops new readers, which is how one slow subscriber froze everything.
- Delivery semantics are a product decision: drop, block with timeout, buffer unboundedly, or disconnect the slow consumer. Make the choice explicit in the doc comment and tests.
- Idempotent shutdown: `Close`, `Stop`, `unsubscribe` should all be safe to call twice (`sync.Once` or state check) and after the parent is closed.
- Goroutine lifecycle: every goroutine needs an exit path tied to a `context` or a done channel; ask "who stops this and when?". Test it deterministically (closed `out`, `Len` back to 0) rather than with `runtime.NumGoroutine`.
- Testing concurrency: always `-race`; wrap blocking calls in a helper with a timeout (`within`) so a deadlock fails one test with a message instead of timing out the binary; use polling with a deadline instead of fixed sleeps; avoid `defer b.Close()` in a test that is expected to deadlock the bus.
- Possible extensions to discuss: typed generic bus, wildcard topics, per-subscriber goroutine with unbounded queue, replay/last-value, metrics for dropped events, `errgroup`-style handlers.

## How to run the conversation

- Ask the engineer to run the tests with `-race` and read the first failure. Then ask them to describe, in words, what each goroutine is doing when `TestSlowSubscriberDoesNotBlockOthers` fails (who holds which lock, who waits for what).
- For the lock issues, ask "what does `RLock` guarantee about the other goroutines in this function?" and "what can `Publish` be doing at the moment unsubscribe closes the channel?" rather than naming the bug.
- When they propose the non-blocking send, ask what the subscriber sees and whether that is acceptable for the audit component; let them argue the trade-offs before settling on a policy.
- For the panics, ask them to list every code path that can close a channel and whether it can run twice.
- Ask "who stops the goroutine in `Once` if nobody ever publishes?" and let them find the leak.
- Leave the negative buffer, topic cleanup, observability of drops and generics for the "what else would you flag?" part.
